# ARCHITECTURE — чому код такий

v1 був один файл на 524 рядки. Аудит знайшов 36 проблем
([`../TG_DICTAPHONE_ISSUES.md`](../TG_DICTAPHONE_ISSUES.md)), з яких
п'ять P0 неможливо було закрити патчами: вони вимагали інших
інваріантів. Цей документ фіксує ці інваріанти, щоб наступна правка їх
не зламала.

## Чотири інваріанти, на яких тримається безпека

### 1. Клавіші йдуть у прив'язану панель, а не «в сесію»

v1 адресував усе як `-t agents`, що означає «активна панель активного
вікна сесії **зараз**». Перемкнув вікно на Mac — і наступний Enter
полетів у чужу панель. tmux ще й матчить імена сесій за префіксом.

v2: `tmuxio.bind_pane()` один раз резолвить immutable pane id (`%0`) і
всі операції йдуть у нього; сесія матчиться точно (`=agents`).
`ensure_pane()` перевіряє, що панель ще жива, і при потребі
переприв'язується — але **повідомляє** про це в UI (`ℹ️ переприв'язано`).

Правило для змін: **ніколи** не додавай tmux-виклик з `-t SESSION`.
Тільки через `tmuxio`, тільки в `PANE["id"]`.

### 2. Fail-closed: спершу перевір, що в панелі агент, і тільки потім надсилай

v1 надсилав текст, а потім дописував попередження «⚠️ не схоже на
агента». Якщо Claude вийшов і в панелі `zsh` — голосова транскрипція
виконувалась як shell-команда.

v2: `handlers._send_confirmed()` читає `pane_current_command` **до**
надсилання. Не агент → нічого не надіслано, показано ⛔️ і окрема кнопка
«Все одно надіслати» (`gf:` замість `go:`). Явний, свідомий override.

Правило: будь-який новий шлях, що вставляє текст, проходить через цю
перевірку.

### 3. Кнопка діє тільки в поколінні, для якого її намалювали

v1: будь-яка стара панель (у т.ч. з-перед рестарту) лишалася бойовою —
кнопки надсилали Enter/Escape/цифри в термінал «як є». Плюс
`drop_pending_updates=False` означало, що кліки, зроблені поки бот
лежав, виконувались після старту.

v2: кожна відмальована панель отримує `gen` (`views._new_gen`), який
їде в `callback_data`. Натиснув старе — «Панель застаріла — ось свіжа»,
у термінал нічого. Додатково:

- `KEY_ALLOW` — білий список клавіш, які панель узагалі може надіслати;
- перед інжекцією (крім `Escape`) перевіряється, що екран **досі**
  `waiting`;
- невідома callback-дія відповідається й ігнорується — **ніколи** не
  трактується як підтвердження (у v1 будь-яка дія, крім `no`, вела до
  надсилання);
- `drop_pending_updates=True`.

### 4. Текст вставляється як текст, а не як послідовність клавіш

v1: `send-keys -l <text>` без `--` (промт, що починався з `-`, ламався
або сприймався як прапорці tmux) і з інтерпретацією переносів рядків
(багаторядковий промт = кілька команд).

v2: `load-buffer` + `paste-buffer -p` (bracketed paste) під
`SEND_LOCK`, потім окремий `Enter`. Якщо Enter не пройшов — бот каже
саме це: «текст УЖЕ в полі вводу», а не бреше «не надіслано».

## Модулі

```
config.py      читає ~/.config/tgbot.env + ENV, валідує, віддає Cfg
tmuxio.py      увесь tmux-I/O: async, з таймаутами, прив'язка панелі
screen.py      ЧИСТІ функції: знімок екрана → ScreenInfo. Без I/O.
views.py       текст панелі + клавіатури + реєстр поколінь
watcher.py     фоновий нагляд за реакцією агента (замість блокування)
transcribe.py  ffmpeg + mlx-whisper (блокуюче, через asyncio.to_thread)
handlers.py    Telegram-хендлери, auth, підтвердження, інжекція клавіш
__main__.py    preflight, реєстрація, post_init, run_polling
```

Чому `screen.py` окремо і без I/O: це найкрихкіша частина (евристики
поверх TUI, який ми не контролюємо). Чиста функція = її можна прогнати
на знімку екрана в тесті. Саме тут були 12 із 36 проблем v1.

## Логіка парсера: що саме вважається діалогом

Головна помилка v1 — «≥2 нумерованих рядки = діалог вибору». Агент
постійно пише нумеровані списки у звичайних відповідях, тому кожна друга
відповідь читалась як «чекає вибору».

v2 вимагає **контексту**:

1. нижній суцільний блок нумерованих рядків (`_option_block`), з
   нумерацією рівно `1..N` (інакше це проза);
2. **і** ознака діалогу: курсор `❯` на рядку блоку, або ask-маркер, або
   рядок-питання безпосередньо над блоком;
3. **і** відсутність нової роботи/tool-виклику **під** блоком (інакше це
   залишки вже відповіданого діалогу вище по екрану).

Далі: маркери роботи (`esc to interrupt`, `thinking…`) шукаються **до**
фільтра шуму — у v1 `NOISE_PREFIXES` викидав рядок, який починається з
`esc to`, раніше, ніж детектор його бачив, тому найнадійніший маркер був
недосяжним. Фільтр шуму тепер застосовується **лише для показу**
(`useful_lines(..., display=True)`).

Стан `unknown`: якщо `capture-pane` не вдався, `capture()` віддає `None`,
і панель каже «не зміг прочитати екран». У v1 помилка читання
перетворювалась на «✅ Панель вільна» — найнебезпечніший різновид
брехні в такому інструменті.

Чекбокси: рахуються **лише всередині діалогу**, тому markdown-списки
`- [x] зроблено` у виводі більше не вмикають клавіатуру навігації.

## Нагляд замість блокування

v1 тримав хендлер у `wait_until_settled()` до 47.5 с. Оскільки PTB
обробляє апдейти по одному, бот на цей час глухнув — включно з кнопкою
⛔️ Перервати, яка потрібна саме тоді. А задачі, довші за 45 с, просто
лишалися без сповіщення.

v2: `watcher.start()` кидає окрему задачу; `concurrent_updates(True)`.
Активність = маркери роботи **або** зміна відбитка екрана
(`fingerprint`, з якого вичищені цифри й спінер-гліфи, щоб тикання
таймера не читалось як робота). Довга задача отримує heartbeat «ще
працює · N хв», стеля `WATCH_MAX_SECONDS` (30 хв) завершується честним
«перестаю стежити», а не тишею.
